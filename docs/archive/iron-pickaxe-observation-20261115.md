## 改进顺序

### P0：让保命独立于模型延迟

当前 `check_and_stabilize` 只由显式 `mc_skill_stabilize` 调用，未成为持续守护。即使调用，函数主要处理浮水、岩浆、进食和极低血停机，并不负责射击/追击时的即时避险。长达 10–42 秒的模型等待期间，Bot 仍站在危险位置挨打。

应由 Bot API 或控制器持续消费真实受伤/死亡事件，在生成阶段也能触发防御和中断重规划。动作由统一仲裁器串行执行，必要时通过 `/stop` 终止当前动作，先用短时防御/脱离火线，再把新快照交给模型。mc-live 承担只读观测。

验收：真实新受伤优先于旧遮挡判断；受击后及时进入保命状态；低血、无可用食物时不能继续以“稳定成功”放行采集/合成；等待模型不再等同于原地无防御。

### P0：撤销整体安全断言，给威胁状态加时效

一个时间点、一个实体的一条射线有遮挡，不能保证其他怪物、移动后的攻击或绕路安全。有顶也不能推导四周封闭。当前模型上下文中的“当前绝对安全”会压过真实伤害，且本轮已经复现。

此前本地修正已覆盖保守遮挡语义，但必须加载到常驻进程，并结合真实伤害、检查范围及快照时间一并验证。新伤害应立即使旧安全推断失效。

### P1：用材料依赖和当前背包驱动下一步

两次在缺圆石时直接合石镐；第二次还在没有木镐时尝试采石。需要为目标物品维护可检查的材料链：木镐 → 圆石 → 石镐/熔炉 → 原铁/燃料 → 铁锭 → 铁镐。死亡后按新背包重算前置条件，而非继续旧计划。

失败回执应提供缺失材料和可立即执行的前置步骤；配方替代材料应按实际库存选择，避免只给出 `cobbled_deepslate`、`cherry_planks` 这样的单个替代配方例子。对铁镐任务的完成判断以实际背包和手持验证。

### P1：让宏技能说明“完成、部分完成、失败”

- 混合采集请求按类型报告允许/拒绝项，明确木镐能挖石头、不能挖铁矿。
- `partial_error` / `last_error` / `interrupted_by` 应提升为调度器能识别的需重规划状态；受伤停止后不能仅因挖过一块就给后续动作正常放行。
- 无候选、不可达、水域过滤、真实保护区和受击要有分别的原因。受击与瞬时寻路失败使用有原因、有时效的失败记录，避免永久冒充保护区。
- 采集目标同时显示目标数、挖掘数、实际入包数；每次宏技能结束附精简的最新位置、生命和背包关键状态。

### P1：恢复材料前先处理威胁和高差

捡包宏技能按固定高度差过滤：本轮关键掉落物 Y=69、Bot Y=74，相差 5 格，被 `4.5` 格过滤条件跳过。模型之后自行走近才取回，却仍在原火力区等待直到死亡。

应返回被跳过物品及原因，优先关键工具，并把危险恢复点与安全落脚位置纳入规划。死亡重复发生时限制无保护的原路捡包，先建立安全位置再处理材料。

### P2：可观测性与部署版本

本轮常驻控制台仍运行旧代码：`run.started` 未包含前次新增的开局快照字段，`mc_status` 仍给出 `safe_in_place:true`，最终报告的系统提示也包含“当前绝对安全”。因此本轮是旧版本基线；本地文件修改不等于进程已经加载。

在控制台和 mc-live 的信息接口暴露已加载版本/启动时间/提示词摘要，并保证实时 JSONL 包含开局快照、受伤、重生和技能内部进度。长宏技能目前只有开始/结束，期间动作和掉血原因难以实时定位。实景第三视角还需减少树叶遮住主体的情况。

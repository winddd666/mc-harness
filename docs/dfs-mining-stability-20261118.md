# DFS 挖矿稳定性专项（2026-11-18）

> 目标：把 `fishbone_scan` 从"能挖到"变成"稳定拿分"——先量死亡/失败边界，再逐条消除。
> 数据来源：`runs/*.json` + `runs/*.events.jsonl` + `/tmp/opencode/*.log`（实机，非沙盘）。

## 1. 数据基线与归因

主实验 35 组（每轮 40 min 预算、2 并发、每轮换新坐标、kit 为 `oak_log 32 / stone_pickaxe 2 / crafting_table / bread 32`）：

| 指标 | 数值 |
|---|---|
| 死亡总数 | 29 次 |
| `mob_attack` | 11 |
| `arrow` | 6 |
| `drown` | 6 |
| `in_wall` | 5 |
| `stalagmite` | 1 |
| 0 钻组 | 13 |

0 钻组拆解：**已修复 4 组**（b03/b12/h12/h13）、**地形贫瘠 3 组**（k02/m06/m10）、**假完成 1 组**（m13）、**测试设计 5 组**（v01–v03 短预算、r1_v5/r2_v5 非本策略）。

m 批次 13 个有效样本：10 成功 / 3 失败，26 颗钻石，成功率 77%，成功组均值 17.9 min。

### 结论：剩余失败不是"策略不会挖"，而是四类工程问题

1. **钻层洞穴被磨死**（`mob_attack` + `arrow` = 17/29，59%）：边退边挨打；在开阔洞穴里直线逃命。
2. **含水层/洞穴场**（`drown` + 相关中止 = 6/29，21%）：同一口井反复中止却原地重试。
3. **换点机制空转**：`reset` 被当成"换地方"按钮，在地下发号施令，把巷道切碎或清空矿井树。
4. **静默空转**：连续返回 `ok:true` 但零收益零位移，模型没有负反馈，只能反复重试。

## 5. "隔墙挖 = 白挖"（2026-11-18 现场发现）

现象：服务端挖掘 API **几乎不校验距离**——全部实机日志里 `out_of_reach` 只出现 1 次。
于是 `fishbone_scan` 在目标层把搜索半径放大到 ±8 后，会隔着 3–8 格石壁把矿打碎；
矿石掉落物留在原矿格（墙后），超出拾取范围，等于白挖。

处理（`cc8b1d9`）：
- `_drop_cell_reachable()`：破矿前判断掉落能否落在拾取范围内（面相邻，或相邻格可站立且离我们一步）；
- 对曼哈顿距离 5 格以上的矿：先沿方向凿通 1–2 格并尝试走到矿旁，够不到就**不破矿**，
  把矿留在世界里等支巷靠近（不标记为不可达）；
- 3–4 格行为暂保持不变（掉落可能落到下方接矿格，实机与既有单测证明可拾取）；
- 新增 `lost_drops` 指标（破矿但没进包的次数），下一轮用它决定是否把阈值收到 2 格。
